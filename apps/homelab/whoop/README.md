# Whoop Data Pipeline

Automated pipeline that scrapes health data from the [Whoop API](https://developer.whoop.com/api) and stores it in a PostgreSQL database.

## Components

| Component | Kind | Description |
|-----------|------|-------------|
| `postgres/cluster.yaml` | CloudNativePG Cluster | 3-node PostgreSQL cluster, auto-generated credentials |
| `postgres/database.yaml` | CloudNativePG Database | Creates the `whoop` database |
| `scraper/cronjob.yaml` | CronJob | Runs daily at 6 AM, scrapes last 7 days of data |
| `scraper/initjob.yaml` | Job | One-off backfill job (2 years of historical data) |
| `scraper/secrets.yaml` | Secret (SOPS) | Whoop OAuth credentials, age-encrypted |
| `scraper/configmap.yaml` | ConfigMap | DB connection info and scraper config |

## Data

~3,500+ records across sleep, workouts, cycles, and recovery metrics (June 2024 – present).

## Secrets

Whoop OAuth credentials (`client_id`, `client_secret`, `access_token`, `refresh_token`) are stored SOPS-encrypted in `scraper/secrets.yaml`. The database password is auto-generated by CloudNativePG and stored in the `whoop-cluster-app` secret.

## Key Problems Solved

**OAuth token expiration:** The Whoop API access token expires and needs to be refreshed. The scraper handles token refresh and writes the new tokens back to the database, which are then read on the next run.

**API rate limiting:** Hitting the Whoop API for 2 years of data at once triggered 429 errors. Solved by batching requests by month and scraping each month separately.

**Job immutability:** Kubernetes Jobs are immutable — you cannot update a running or completed Job. When changes were needed, the Job had to be deleted and recreated.

**Finding the executable:** The scraper container's entrypoint wasn't obvious. The correct path inside the container is `/app/.venv/bin/whoop-scraper`.

**Database host:** CloudNativePG exposes the read-write service at `<cluster-name>-rw.<namespace>.svc.cluster.local`. The configmap uses `whoop-cluster-rw.whoop.svc.cluster.local`.
